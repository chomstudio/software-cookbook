# GitHub Pages版 逆引きマニュアル仕様書

最終更新日: 2026-10-12

## 目的

既存のMarkdown文書を元原稿として、GitHub Pages上でジャンル、アプリ名、項目名、本文を検索し、読みやすく閲覧できるサイトを作成する。

初回設定後は、公開対象ブランチへ文書をpushするだけで、文書一覧と検索対象と公開内容が更新される。HTMLへの手動変換、検索用データの手動編集、Codexによる都度のアップロードを不要とする。

本書は実装前の仕様である。今回の作業対象は本書の作成のみとし、サイト実装やGitHubの設定変更は別作業とする。

## 基本方針

- 逆引き文書は `cookbooks/` 配下にまとめる。既存ジャンルフォルダを一階層深く配置し、ジャンル名、ファイル名、本文、見出し、目次は維持する。
- 文書へのFront Matter、検索用タグ、専用IDの追加を要求しない。
- HTML、CSS、プレーンJavaScriptで構成する静的サイトとし、サーバー処理、データベース、Sitesを利用しない。
- ActionsではMarkdownの解析、検索用JSONの生成、公開用ファイルの収集を行う。文書本文のHTML化は閲覧時にブラウザ内のJavaScriptで行う。
- 公開内容はGitHub Actionsが取得した同一コミットに揃える。GitHub APIや外部のrawファイルから閲覧時に原稿を取得しない。
- 文書は個人の調査記録として扱い、サイト上でもその旨を簡潔に説明する。
- 通常のGitHub Pagesによる一般公開を前提とする。利用者認証や限定公開は本仕様の対象外とする。

## フォルダ構成

既存ジャンルフォルダは `cookbooks/` 配下へ移動済みである。サイト実装時はこの配置を維持し、以下のサイト構築用ファイルを追加する。文書の再移動は不要である。

```text
software-cookbook/
├ AGENTS.md
├ cookbooks/
│ ├ browser/
│ ├ development/
│ ├ dtm/
│ └ movie/                  今後のジャンルもこの階層に追加
├ codexdocs/
│ └ spec.md
├ index.html
├ web/
│ ├ app.js
│ ├ styles.css
│ └ lib/                    共通のMarkdown解析・見出しID処理
├ scripts/
│ └ build-site.mjs
├ .github/
│ └ workflows/
│   └ pages.yml
├ package.json
├ package-lock.json
└ .gitignore
```

- `cookbooks/` は逆引き文書とその参照資産の置き場とし、サイト構築用ファイルや生成データは置かない。
- `index.html` は検索と閲覧の共通入口とする。
- `web/` は表示用コード、`scripts/` は公開用データの生成処理とする。
- 生成物は `_site/` に出力し、Git管理から除外する。既存の除外設定があれば維持する。
- `_site/` にはトップページ、表示用資産、検索用データ、対象Markdown、文書が参照する公開用ローカル資産だけを収める。
- リポジトリ全体を公開成果物としてアップロードしない。
- 利用可能な実装ができた段階で、初回設定と利用方法を説明する `README.md` を追加する。既存の説明書があれば必要範囲のみ更新する。

## 文書の自動検出

### 検出条件

- `cookbooks/` 直下のジャンルフォルダ以下だけを再帰的に走査し、拡張子 `.md` のファイルを検出する。
- 最初のレベル1見出しの末尾が `逆引きマニュアル` である文書を対象とする。末尾の語を除いた文字列をアプリ名とする。
- ジャンル名は、`cookbooks/` からの相対文書パスの先頭フォルダ名をそのまま使用する。例えば `cookbooks/movie/ffmpeg.md` はジャンル `movie`、アプリ名 `ffmpeg` となる。
- カタログ、検索データ、閲覧URLの文書パスは `cookbooks/` からの相対パスとする。例えば `movie/ffmpeg.md` を使用し、`cookbooks/` 自体をジャンルとして扱わない。
- 固定のジャンル一覧やアプリ一覧は設けない。新しいジャンルフォルダと文書も同じ条件で自動検出する。
- レベル1見出しがない文書や対象タイトルに一致しない文書は検索・公開から除外し、走査結果をActionsログへ出す。
- フォルダ名、ファイル名の変更と削除は、毎回の全件生成によって公開内容にも反映する。

### 除外条件

- `cookbooks/` の外部、`cookbooks/` 直下のMarkdown、ドットで始まるフォルダは文書の検出対象外とする。
- `AGENTS.md`、`AGENTS-draft.md`、`README.md`、`requests.md`、`prompt.md` は場所にかかわらず対象外とする。
- シンボリックリンクは辿らず、`cookbooks/` の外部にある文書や参照資産は収集しない。
- 検出件数がゼロの場合は生成を失敗させ、空のサイトを公開しない。

## Markdownの解析と検索データ

### 見出しと本文の抽出

- Markdownパーサーの構造を利用する。単純な行の正規表現だけで項目を分割しない。コードブロック内の `#` を見出しとして扱わない。
- レベル2から6の各見出しについて、見出し直後から次の見出し直前までを、その見出しに直接属する本文として検索レコードにする。
- レコードには親見出しの階層を持たせる。下位見出しの本文に一致した場合は、その下位見出しへ移動する。
- 子見出しの本文を親レコードにも重複収録しない。親見出しの語は子レコードの検索対象とする。
- 直接の本文がない見出しも検索対象にする。レベル2だけの項目、レベル3の項目、レベル4以降の補足を扱えるようにする。
- レベル1見出しと最初のレベル2見出しの間にある説明文は、文書概要レコードにする。項目がない文書も一覧表示と概要検索を可能にする。
- 冒頭の目次は、フラグメントリンクだけからなる一覧を目次ブロックとして検出し、検索本文から除外する。表示時は既存目次を保持する。
- `最終更新日:` の行は検索本文から除外し、表示用メタデータとして抽出する。存在しない文書には日付を補わない。
- `修正履歴` とその下位の本文も検索対象とし、検索結果に見出しの名称を表示する。
- コードブロック、インラインコード、表、箇条書き、引用の文字列も本文検索の対象とする。

### データの構成

- `data/catalog.json` に文書パス、ジャンル、アプリ名、タイトル、任意の最終更新日、見出し一覧、配信ファイルへのパスを収める。
- `data/search-index.json` に文書パス、見出しID、見出し階層、項目名、検索用の本文文字列を収める。アプリ名とジャンルは文書情報と結合して検索する。
- 両JSONに形式バージョンと元コミットSHAを持たせる。
- 配信するMarkdownとデータファイル名には内容ハッシュを付け、文書追加・変更後に古いデータが混在しにくい構成にする。入口のカタログは再取得する。
- 生成順序は文書パス順、文書内の出現順に固定し、同じ入力から同じ内容を生成する。

## トップページと検索

### 初期表示

- サイト名、検索欄、ジャンルとアプリの絞り込み、ジャンル別の文書一覧を表示する。
- 検索欄には「ジャンル・アプリ名・項目名・本文を検索」と用途を示す。
- 検索語が空の場合は文書一覧を表示する。全項目の検索結果を大量に展開しない。
- ジャンルとアプリの選択肢はカタログから生成する。ジャンル変更時はアプリ候補を連動させる。
- 外観は日本語の実用文書を読むことを優先し、装飾より検索と本文の読みやすさを重視する。

### 一致条件と並び順

- ジャンル、アプリ名、アプリのファイル名、見出し階層、本文を横断して検索する。
- 検索語と検索対象をUnicode NFKCで正規化し、英字の大文字小文字を区別しない。元の表示文字列は変更しない。
- 空白区切りの語をAND検索する。各語は同じ検索レコードのいずれかのフィールドに含まれていればよい。
- 日本語は単語分割せず部分一致とする。正規表現、OR演算子、引用符による専用構文、曖昧検索、同義語辞書は初期実装の対象外とする。
- 検索結果は現在の項目名、親見出し、アプリ名・ファイル名、ジャンル、本文の順に一致を評価する。各語が最も強く一致したフィールドの点数を合計し、降順に並べる。
- 点数は項目名5、親見出し4、アプリ名・ファイル名3、ジャンル2、本文1とする。同点は文書パス順、文書内の出現順とする。
- 絞り込み条件は検索語に対してANDで適用する。
- 日本語IMEの変換中は検索を更新しない。入力確定後は約200msの待機を置いて更新し、検索ボタンまたは `Enter` でも実行できる。

### 結果表示

- 一件を一つの見出しまたは概要として表示する。ジャンル、アプリ名、見出し階層、本文抜粋を添える。
- 抜粋は本文の一致箇所を優先し、約120文字を表示する。本文に一致がない場合は先頭を表示する。
- 検索結果内の一致文字列を強調する。正規化によって文字数が変わる場合にも元文字列の範囲へ対応付け、検索語をHTMLとして挿入しない。
- 総件数を表示し、初回は50件まで表示する。追加表示で残りを閲覧できる。
- 該当なし、読み込み中、取得失敗を区別して表示する。失敗時は再試行操作を用意する。
- 検索データは初回検索時に一度だけ取得し、そのページを開いている間は再利用する。検索語を外部サービスへ送信しない。

## 文書の閲覧

### 表示と移動

- 一つのHTML入口で一覧、検索結果、文書表示を切り替える。文書を選ぶと配信済みMarkdownを取得し、ブラウザ内でHTMLに変換する。
- 文書は全文表示し、検索結果から選んだ見出しへスクロールする。見出しリンクをコピーして直接共有できるようにする。
- 文書閲覧時も検索欄へ戻れる導線、ジャンルとアプリ名、レベル2・3の目次を提供する。既存本文にある目次は書き換えない。
- 日本語本文の行間と本文幅を確保する。コードは等幅フォントとし、長いコードと表はその領域内だけ横スクロールさせる。
- 見出し、段落、強調、箇条書き、番号付き手順、リンク、引用、区切り線、コード、GFMの表・打ち消し線・タスクリストを表示できること。
- 既存のコードフェンスに未知の言語指定があっても、コード本文を欠落させない。
- 元のMarkdownへのリンクを用意する。JavaScript無効時はその旨を表示し、手書きの文書一覧を保守することは要求しない。

### URLとリンクの扱い

- URLは `index.html?doc=movie%2Fffmpeg.md#見出しID` の形とし、検索語と絞り込みもクエリに保存する。履歴移動、再読み込み、直接アクセスを扱う。
- クリーンURLやPages側のリライトルールを要求しない。リポジトリ名を含むPagesのサブパスとルート公開の双方で動作する相対URLを使う。
- 見出しIDはGitHub互換のslug生成ライブラリを使い、同名見出しには出現順の接尾辞を付ける。生成処理と閲覧処理で同じライブラリとバージョンを使う。
- 既存の文書内目次リンクが同じ見出しへ到達することを検証する。参照切れがある場合は文書を自動修正せずログに記録する。
- 対象Markdownへの相対リンクは、元文書のフォルダを基準に解決し、閲覧URLへ変換する。フラグメントも保持する。
- ローカル画像などの参照資産は、対象文書からの参照に限って `cookbooks/` 内から収集する。Markdownの相対参照、参照形式リンク、画像URLを解析して配信URLへ変換する。
- 外部HTTPSリンクは通常のリンクとして保持する。ローカル資産の欠落は生成エラーとし、対象外Markdownへのリンクは閲覧可能な外部URLが設定されない限り警告する。
- 文書または見出しが削除・改名されているURLでは、文書不存在の案内または文書先頭への案内を表示する。過去URLの自動転送は要求しない。

### 安全な表示

- Markdown由来の生HTMLは実行せず文字列として扱う。変換後HTMLはサニタイズし、スクリプト、イベント属性、危険なURLスキームを除去する。
- URLで指定された文書パスはカタログの登録内容と照合する。任意URLやルート外のファイルを取得しない。
- ローカル資産も `cookbooks/` 内で解決できるものに限定する。認証情報をクライアントコードや公開成果物へ含めない。

## 自動生成と公開

### ワークフロー

1. 公開対象ブランチへのpush、または `workflow_dispatch` により実行する。
2. 対象コミットを取得し、Node.js環境と固定された依存関係を `npm ci` で準備する。
3. 文書を検出・解析し、カタログと検索用JSONを全件生成する。
4. `_site/` に表示用ファイル、生成データ、対象Markdown、参照資産を収集する。
5. データ構造、参照先、見出しIDを検証する。
6. `actions/upload-pages-artifact` で成果物を保存し、`actions/deploy-pages` で公開する。

- 初期の公開対象ブランチは、現在のリポジトリのブランチに合わせて `master` とする。別ブランチへ変更する場合はワークフローとPagesの環境ルールを合わせて変更する。
- push対象パスをジャンル一覧に限定しない。新しいジャンルを追加してもワークフロー編集を必要としない。
- 生成物を元ブランチへコミットしない。文書更新後にGitの差分が自動生成物で増えないようにする。
- 公開ジョブは `contents: read`、`pages: write`、`id-token: write` と `github-pages` 環境を使用する。生成ジョブには必要最小限の権限を付与する。
- 同時実行を制御し、古い実行が新しい公開内容を上書きしないようにする。
- 解析・検証・生成が失敗した場合は新しい成果物を公開しない。直前に成功したサイトを維持し、Actionsログに原因とファイル名を出す。

### 初回設定と通常運用

- 初回のみ、GitHubリポジトリの `Settings`＞`Pages`＞`Build and deployment`＞`Source` を `GitHub Actions` に設定し、必要なActionsと環境の実行を許可する。
- リポジトリの公開状態と契約がGitHub Pagesの利用条件を満たすことを確認する。
- 通常は `cookbooks/<ジャンル>/` 内のMarkdownを既存ルールどおり編集し、公開対象ブランチへpushする。新規文書も同じ配置と対象タイトルで記述するだけで検索対象になる。
- Git操作はユーザーが行う。サイト生成のためにCodexが勝手にコミットやpushを行う運用には変更しない。
- 反映はpush直後ではなくActionsの公開成功後となる。失敗時はActionsから原因を確認し、修正して再pushまたは再実行する。

## 技術構成と依存関係

- 生成処理とブラウザ処理はJavaScriptを使用する。Node.jsは実装時点のLTS系を選び、ワークフローでメジャーバージョンを固定する。
- Markdownパーサー、GitHub互換slug生成、HTMLサニタイズには保守されている既存ライブラリを使用する。具体的な採用ライブラリは実装時に互換性を確認して決定する。
- Markdown解析と見出しID生成を共通モジュール化し、生成時と閲覧時のずれを防ぐ。
- 依存関係は `package.json` とロックファイルで管理する。ブラウザ用資産も公開成果物へ収め、実行時のCDN依存を避ける。
- 外部ライブラリの必要なライセンス表示を保持する。プロジェクト自身へのライセンス追加は行わない。
- Jekyllなどによる文書HTMLの生成は行わない。必要ならブラウザ用JavaScriptのバンドル処理のみ生成工程に含める。

## 検証と受け入れ条件

- `cookbooks/` 配下に配置済みの6文書が対象として検出され、サイト実装によってジャンル名、ファイル名、原稿内容、ジャンル内の相対配置が変更されないこと。
- `cookbooks/` 内の新しいジャンルに対象文書を一つ追加してpushすると、設定や文書一覧を編集せず一覧と検索に反映されること。
- `cookbooks/` の外部に同じ対象タイトルのMarkdownがあっても検出されず、`cookbooks/` 自体がジャンル名にならないこと。
- 文書・見出しの編集、削除、ファイル移動が次回生成で反映されること。
- `movie`、`ffmpeg`、`ステップ録音`、`h264_nvenc` が、それぞれジャンル、アプリ名、項目名、本文の検索として機能すること。
- `FL Studio ステップ` の複数語検索、全角英数字、大文字小文字、絞り込み、検索語なし、該当なしを扱えること。
- コード内の見出し風文字列、重複見出し、レベル2だけの項目、レベル4の補足、日本語・記号付きの見出しを正しく扱えること。
- 冒頭目次による本文一致の重複がなく、修正履歴は検索できること。
- 結果から該当見出しへ移動でき、直接URL、再読み込み、ブラウザの戻る・進むで状態を復元できること。
- コードと表、既存の目次リンク、相対Markdownリンク、画像が読めること。
- `AGENTS.md`、仕様書、指示書、依存関係、Gitメタデータが検索にも公開成果物にも入らないこと。
- 不正な文書パスとMarkdown中の実行可能HTMLを安全に扱えること。
- データ取得失敗、文書不存在、生成失敗が無言の空白画面にならないこと。
- Windows 11の最新安定版Chrome、Edge、Braveで確認する。幅約360pxでも本文全体が横にはみ出さず、検索・一覧・閲覧をキーボードで操作できること。
- ローカル確認は一時HTTPサーバーを利用する。リポジトリ名を含むサブパスでも取得と移動を検証する。
- 実装時は生成・検索・見出しリンクの意味のある自動検証と、ブラウザでの表示確認を行う。実際の公開確認は初回設定後に行う。

## 対象外と将来の拡張

- サイト上での原稿編集、ログイン、コメント、外部検索サービス、AI検索、検索エンジン向けの文書ごとのHTML生成は初期仕様に含めない。
- 現状の文書量では検索JSONをブラウザに読み込む方式とする。量が増えて転送や検索が重くなった場合は、インデックス分割やWeb Workerを検討する。
- 正式名称以外のアプリ名やジャンルの日本語別名は、必要になった時点で表示・検索用設定として追加する。通常の文書追加に登録作業は要求しない。
